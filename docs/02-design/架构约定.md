# 飞机对战游戏项目代码架构约定

版本：v0.1  
日期：2026-10-20  
适用工程：DogfightThreatAI 客户端，以及后续的 GatewayServer、LogicServer、Protocol 工程

## 一、目的与适用范围

本约定用于统一项目代码的分层方式、目录结构、配置与运行状态的边界，以及提交前的验证标准。其目的是降低多人协作中的耦合和返工，并保证模拟逻辑可以同时用于客户端和逻辑服务器。

本约定不涉及具体玩法设计，也不替代需求文档、系统设计文档和接口文档。

本约定描述目标结构。目录树与表格中标注“后续”的类型尚未实现。

## 二、总体架构思路

本项目采用“数据先行、分层连接”的组织方式。开发新功能时，先确定需要哪些数据、数据由谁持有、何时变化，再决定代码放在哪一层。

### 2.1 数据先行

项目中的数据分为三类。

| 数据类型 | 说明 | 存放形式 | 示例 |
|---|---|---|---|
| 配置数据 | 运行时不发生变化 | ScriptableObject 或纯 struct | AircraftData、ArenaConfig |
| 运行状态 | 每个模拟步或每帧变化 | struct | FlightState |
| 事件 | 在某一时刻发生一次 | struct 与事件列表 | 命中、击毁、得分 |

代码负责定义数据的“种类”，资产负责提供数据的“实例”。一类数据对应一个类型，一个实例对应一个资产；行为代码按能力复用，不按实例复制。

因此，增加一架飞机、一档 AI 难度或一种武器时，只需新增资产，不需要修改代码；只有增加新的数据种类或机制时，才需要编写新类型和新系统。

### 2.2 用胶水连接，而不是让代码互相调用

模拟层只负责计算，表现层只负责显示。两者之间通过状态快照和事件列表连接：

    输入源 → BattleSimulation.Tick() → 状态快照 + 事件列表 → 视图 / UI / 网络

胶水层负责读取输入、调用模拟、把结果交给表现，但不包含飞行、伤害、胜负等规则。

这样做的直接结果是：模拟层不依赖 Unity，可以放入逻辑服务器；表现层可以替换为观战、回放或其他视图，而不需要修改模拟代码。

### 2.3 系统建立在数据之上

对局状态由 BattleSimulation 统一持有和推进。场景中的 Bootstrap 只负责创建和连接对象，视图只读取状态。项目不设置全局 GameManager，也不使用静态单例保存对局状态。

这样，同一进程可以运行多场对局，测试可以独立创建模拟实例，服务器也可以复用同一份逻辑。

### 2.4 三个判断问题

编写新代码前，先回答三个问题：

1. 这段代码是否需要在逻辑服务器上运行？
2. 这是配置数据还是运行状态？
3. 这段代码属于计算还是表现？

三个问题的答案，基本决定了代码应放入 Core、Gameplay 还是胶水层。

## 三、程序集与分层

### 3.1 程序集划分

本项目客户端目前划分为五个程序集。

| 程序集 | 职责 | Unity 依赖 |
|---|---|---|
| DogfightThreatAI.Core | 飞行、碰撞、边界、威胁评估、AI 决策、对局模拟 | 不得引用 |
| DogfightThreatAI.Gameplay | MonoBehaviour、视图、输入实现、ScriptableObject 配置、胶水代码 | 允许引用 |
| DogfightThreatAI.UI | 开始界面、面板、菜单设置；独立于战斗模拟，可单独进行 UI 流程测试 | 允许引用 |
| DogfightThreatAI.Tests.EditMode | 纯逻辑单元测试 | 仅测试环境 |
| DogfightThreatAI.Tests.Menu | 开始界面 PlayMode 流程测试 | 仅测试环境 |

依赖方向如下：

    Gameplay → Core
    Tests.EditMode → Core、Gameplay
    UI → UnityEngine.UI
    Tests.Menu → UI、UnityEngine.UI

Core 不得引用 Gameplay、UI、Network 等上层程序集。

Core 程序集的 `noEngineReferences` 已设置为 `true`。在该程序集中引用 UnityEngine 将导致编译失败。该设置用于保证模拟代码可以脱离 Unity 运行。

### 3.2 分层原则

1. 模拟与表现分离。模拟层负责计算状态，表现层负责读取状态并绘制，两者不互相调用内部逻辑。
2. 配置与状态分离。运行时不变的数值放入 ScriptableObject；每帧变化的数值放入 struct。
3. 胶水层只负责连接。胶水代码可以同时接触输入、模拟和视图，但不得包含飞行、伤害、胜负等规则。

## 四、数据流与状态边界

对局中的主要数据流如下：

    输入源（键盘、AI、网络）
              ↓
    BattleSimulation.Tick()
              ↓
    状态快照 + 事件列表
              ↓
    视图、UI、网络

相关约定：

1. 状态是事实源。位置、速度、血量、分数等结果应以状态快照为准。
2. 事件用于表现和通知，包括开火、命中、击毁、得分等。事件丢失不应改变战斗结果。
3. `transform` 仅作为表现层的承载，不得作为位置的事实源。
4. 事件只能由模拟层向外发出。视图和 UI 接收事件后，不得反向修改模拟层数据。

### 5.3 新代码归属判断

新增代码时，按以下顺序判断：

1. 该代码是否需要在逻辑服务器上运行。需要时放入 Core。
2. 该代码是否只与显示、输入或 Unity 生命周期有关。是则放入 Gameplay 或 UI。
3. 该代码是否仅用于连接上述两部分。是则放入 Gameplay 的胶水层。

常见代码类型与目录对应关系如下：

| 代码类型 | 目录 |
|---|---|
| 纯逻辑、纯算法 | `Scripts/Core/<领域>/` |
| 武器与战斗规则 | `Scripts/Core/Combat/` |
| ScriptableObject 配置类 | `Scripts/Gameplay/Config/` |
| Unity 胶水、MonoBehaviour | `Scripts/Gameplay/<领域>/` |
| 视图与输入实现 | `Scripts/Gameplay/View/`、`Scripts/Gameplay/Input/` |
| UI | `Scripts/UI/` |
| 客户端网络胶水 | `Scripts/Network/` |
| 服务器逻辑 | `src/server/` |
| 共享协议 | `src/shared/Protocol/` |
| 单元测试 | `Tests/EditMode/` |
| 配置资产 | `Settings/<领域>/` |

### 5.4 目录与文件规则

1. 一个公开类型对应一个文件，文件名与类型名一致。
2. 命名空间应与目录结构一致。例如 `Core/Flight/FlightModel.cs` 使用 `DogfightThreatAI.Core.Flight`。
3. 不得建立 `Utils`、`Common`、`Helpers` 等职责不明确的目录。无法确定归属时，应先与模块负责人确认。
4. `.asset`、prefab、贴图等资源不得放入 `Scripts` 目录。
5. 移动 `.cs` 文件时，`.meta` 文件必须一同移动。宜在 Unity 编辑器内移动，或使用 `git mv` 同时移动 `.cs` 与 `.cs.meta`。
6. 新建 asmdef 应具有明确理由，例如需要独立的编译边界或平台限制。不得为少量文件建立空壳程序集。
7. `Scripts/Controllers`、`Scripts/Data`、`Scripts/Managers` 为旧结构残留，不再新增代码，后续统一清理。
8. 纯 AI 逻辑后续放入 `Core/AI`，不得在 `Scripts/AI` 中编写 MonoBehaviour 形式的 AI 决策。
9. 网络协议放入 `src/shared/Protocol`；客户端网络胶水放入 `Scripts/Network`；服务器逻辑放入 `src/server`。

## 六、配置与内容扩展

项目的扩展方式分为内容扩展和功能扩展两类。

| 扩展类型 | 定义 | 是否需要修改代码 |
|---|---|---|
| 内容扩展 | 增加已有种类的新实例 | 不需要 |
| 功能扩展 | 增加新的种类或机制 | 需要 |

常见操作如下：

| 操作 | 实现方式 | 是否修改代码 |
|---|---|---|
| 增加一架飞机 | 新建 AircraftData 资产，并在 AircraftCatalog 中登记 | 否 |
| 调整飞行手感 | 修改 AircraftData 数值 | 否 |
| 增加一档 AI 难度 | 新建 AiProfile 资产 | 否 |
| 调整边界规则数值 | 修改 ArenaConfig 资产 | 否 |
| 增加一种武器 | 新建 WeaponData 资产并登记 | 否 |
| 增加一种全新机制 | 新增类型、系统与测试 | 是 |
| 增加一张地图 | 新增地图数据资产 | 视地图机制而定 |

判断标准为：代码定义“种类”，数据定义“实例”。增加实例不修改代码，增加种类才编写代码。

## 七、武器与战斗规则

本项目第一阶段的武器范围为机炮与导弹。追踪导弹作为第二阶段目标，视进度决定是否实现。

### 7.1 机炮

- 采用命中扫描（hitscan），不生成飞行子弹实体。
- 在 Core 中使用线段与圆的相交判定，不使用 Unity 的 Raycast。
- 配置项包括射速、伤害、射程、散布与冷却。
- 由模拟层判定命中与伤害，客户端只播放开火与命中表现。
- 产生事件：`GunFired`、`Hit`、`Destroyed`。

### 7.2 导弹

第一阶段的导弹为直线飞行，用于验证生成、飞行、碰撞、伤害与回收流程。

追踪导弹作为第二阶段内容，采用自动锁定方式：

- 发射时在前方锥形范围内选择最近的敌方目标，无目标则直线飞行。
- 导弹按最大转向速率朝目标方向转向，转向速率低于飞机，玩家可通过急转摆脱。
- 导弹具有寿命与近炸引信，超过寿命后自毁。
- 目标死亡、超出范围或导弹寿命结束时，导弹转为直飞或自毁。
- 锁定与命中判定均在模拟层完成，客户端只显示锁定框与事件表现。

若第二阶段未实现，应在结题文档中说明与立项书的差异：立项书包含导弹追踪，当前版本为直线导弹。

### 7.3 数据与状态

| 类型 | 内容 | 存放位置 |
|---|---|---|
| WeaponData | 武器配置资产，ScriptableObject | Settings/Weapons |
| WeaponSpec | 纯配置结构 | Core/Config |
| 武器运行时状态 | 冷却、弹药、锁定目标 | 飞机运行时状态 |
| 武器事件 | 开火、发射、命中、自毁 | Core（BattleEvent 的事件类型） |

武器配置应通过稳定 ID 引用，不在代码中硬编码。冷却、弹药与锁定目标属于运行状态，不写入 ScriptableObject。

### 7.4 网络与 AI

- 武器判定由逻辑服务器执行，客户端不得自行判定命中。
- 服务器广播开火、发射、命中与击毁事件；客户端根据事件播放表现。
- AI 使用与玩家相同的武器系统。AI 的射击纪律、瞄准误差与规避行为由 AiProfile 控制。
- 若实现追踪导弹，威胁网格应将导弹位置、速度与追踪状态计入威胁值。

### 7.5 分工

| 工作 | 岗位 |
|---|---|
| 机炮与导弹规则、碰撞、伤害 | A |
| AI 射击与规避、威胁网格接入 | B |
| 武器事件、快照与协议 | C、D |
| 武器资产、尾迹、爆炸、锁定 UI | E |

## 八、开发与提交规范

### 8.1 编码前的判断

编写新代码前，应先回答以下三个问题：

1. 该代码是否需要运行在逻辑服务器上。需要时，必须使用纯 C# 实现。
2. 该数据属于配置还是运行状态。配置写入 ScriptableObject，状态写入 struct。
3. 该代码属于计算还是表现。计算放入 Core，表现放入 Gameplay。

### 8.2 提交前检查

提交或合并前，应满足以下条件：

- 编译无报错。
- EditMode 测试全部通过。
- Core 中不存在 UnityEngine 引用。
- 数值来自配置资产，未硬编码在代码中。
- 每帧执行路径中未产生不必要的堆分配。
- 未新增全局单例。
- 未跨场景持有场景物体引用。
- 场景与 prefab 的修改已保存。
- 修改过场景或 prefab 时，已在 Unity 中确认无 Missing 引用。

### 8.3 场景与预制体

场景和 prefab 的修改宜通过 Unity 编辑器或 UnityMCP 完成，以便由 Unity 负责序列化。修改完成后必须保存。

版本控制中不得使用“Discard All Changes”清除未提交内容，以免丢失场景或资产修改。

## 九、常见问题

**问：视图中能否直接修改血量或位置？**  
答：不能。血量与位置属于模拟状态，应由模拟层修改。视图只读取状态和事件。

**问：是否需要新增 GameManager 统一管理所有飞机？**  
答：暂不新增。对局状态由 BattleSimulation 管理，场景初始化由 Bootstrap 负责。如确需新增全局对象，应先明确其职责和生命周期。

**问：修改 asset 数值后，Play 模式中未生效。**  
答：FlightModel 在 Awake 时将配置复制到只读字段。应停止 Play，修改 asset 后重新运行。

**问：Core 中能否使用 Mathf 或 Vector2？**  
答：不能。数学运算使用 MathF，二维向量使用 Vec2。需要与 Unity 类型互转时，在 `Gameplay/Adapters` 中完成。

**问：新功能无法确定归属。**  
答：按照 8.1 的三个问题判断。仍无法确定时，与模块负责人确认后再编码。

## 十、附则

本约定自发布之日起执行。新增程序集、调整 Core 边界、将运行状态写入 ScriptableObject 三类变更，应先经团队讨论后实施。
